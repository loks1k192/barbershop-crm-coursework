## Архитектурный стиль

Barber CRM — микросервисная платформа за единым **API Gateway** (Go, chi, JWT).
Исходные сервисы `staff`, `booking`, `client`, `analytics` общаются по gRPC, обмениваются
событиями через Kafka и хранят данные в отдельных БД (PostgreSQL, ClickHouse, Redis).

Курсовой проект добавляет сервис **core** с **единой реляционной БД `barbershop`**
(PostgreSQL 16). Причина — требования к целостности: инварианты, охватывающие мастеров,
смены, клиентов, записи и оплаты, можно обеспечить внешними ключами, ограничениями и
транзакциями только в одной БД. Шлюз проксирует `/api/core/*` в core после проверки
JWT и передаёт идентификатор пользователя заголовком `X-User` (он попадает в аудит).

## Сервис core: слои

| Слой | Пакет | Ответственность |
|---|---|---|
| HTTP | `internal/api` | Маршруты chi, middleware (RequestID, логирование, recover, таймаут, X-User), разбор и валидация входных данных, фильтры, белый список сортировки, пагинация, OpenAPI |
| Данные | `internal/store` | Параметризованный SQL (pgx), вызов функций БД, отчёты из `sql/queries` (встроены в бинарник) |
| Транзакции | `internal/db` | `InTx`: уровень изоляции, `SET LOCAL crm.app_user`, повтор при 40001/40P01 |
| Ошибки | `internal/apperr` | SQLSTATE → HTTP-статус и код ошибки |
| Миграции | `internal/migrate`, `migrations/` | Версионные миграции в транзакциях, advisory-lock, контрольные суммы |
| CLI | `cmd/migrate`, `cmd/importer`, `cmd/concurrency-demo` | Миграции, пакетная загрузка CSV, демонстрация конкурентного доступа |

## Распределение логики между приложением и СУБД

| В PostgreSQL | В приложении |
|---|---|
| Инварианты данных: PK/FK/UNIQUE/CHECK, EXCLUDE (непересечение), правила смен, переходов статусов, оплат, отзывов, бонусов | Формат и обязательность входных полей — быстрая обратная связь по каждому полю (CHECK в БД — последний рубеж) |
| Составные операции (`book/complete/cancel/reschedule_appointment`) — атомарны, вызываются любым клиентом БД одинаково | Аутентификация (шлюз), выбор уровня изоляции и повтор транзакций |
| Автоматизация: история статусов, аудит, бонусные счета, уровни лояльности | Преобразование ошибок СУБД в HTTP, пагинация, сортировка |
| Аналитика: представления, MV, запросы с оконными функциями | Планировщик обновления MV, формирование JSON |

Бизнес-правила не дублируются: например, пересечение записей проверяет только
EXCLUDE-ограничение, приложение лишь превращает `23P01` в `409 time_slot_conflict`.

## Безопасность доступа к БД

* Приложение подключается ролью **`crm_app`**: нет DDL, нет прямой записи в финансовые
  таблицы, `UPDATE` записи — только столбцов `status`, `comment`, `cancel_reason`;
  составные операции выполняются `SECURITY DEFINER`-функциями с фиксированным
  `search_path`.
* Миграции и наполнение — роль **`crm_owner`**; отчёты для BI — **`crm_readonly`**.
* Пароли передаются через `.env` (в git только `.env.example`); весь SQL параметризован,
  поля сортировки берутся из белого списка.
