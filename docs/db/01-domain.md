# 1. Предметная область и требования

## 1.1. Описание предметной области

**Объект автоматизации:** сеть барбершопов из нескольких филиалов в одном городе
(часовой пояс `Europe/Moscow`). Исходный проект Barber CRM автоматизировал работу
частного барбера (расписание, онлайн-запись, клиенты, простая аналитика). В курсовом
проекте он развит до CRM сети: появились филиалы, общий каталог услуг, индивидуальные
цены мастеров, оплаты, бонусная программа лояльности, отзывы, история статусов и аудит.

**Участники процессов:**

| Роль | Что делает в системе |
|---|---|
| Клиент | Выбирает мастера, услуги и время, записывается онлайн, приходит на визит, оплачивает, оставляет отзыв, копит и тратит бонусы |
| Администратор филиала | Ведёт справочники (филиалы, мастера, услуги), составляет график смен, записывает клиентов по телефону, отмечает неявки, загружает клиентские базы |
| Барбер (мастер) | Работает по сменам, оказывает услуги, подтверждает начало и окончание визита |
| Управляющий сетью | Анализирует выручку, загрузку мастеров, отток и сегменты клиентов |
| CRM-система | Рассчитывает свободные слоты, проверяет бизнес-правила, начисляет бонусы, ведёт аудит, обновляет отчёты |

## 1.2. Основные бизнес-процессы

1. **Ведение справочников** — филиалы, категории и каталог услуг, мастера, их
   персональные цены и длительности услуг (у мастеров разного грейда цена одной и той же
   услуги отличается), настройки онлайн-записи мастера.
2. **Планирование графика** — для мастера на конкретную дату создаётся смена в
   конкретном филиале. Смена должна лежать внутри часов работы филиала. Смену нельзя
   сократить или удалить, если в выпадающем интервале есть активные записи.
3. **Запись клиента** — клиент (онлайн) или администратор (телефон, «с улицы») выбирает
   мастера, набор услуг и дату; система рассчитывает свободные слоты с учётом смены,
   шага сетки, длительности услуг и уже существующих записей. При записи клиент
   идентифицируется по телефону (при первой записи создаётся карточка клиента и бонусный
   счёт), цены услуг фиксируются на момент записи.
4. **Обслуживание** — запись проходит жизненный цикл
   `scheduled → confirmed → in_progress → completed`; возможны `cancelled`
   (с обязательной причиной) и `no_show` (неявка). Финальные статусы не меняются.
   Все переходы журналируются.
5. **Расчёт и лояльность** — по завершении визита клиент оплачивает услуги (наличные,
   карта, онлайн) и может списать бонусы (не более 30 % чека и не более остатка).
   С оплаченной деньгами части начисляются бонусы по ставке уровня
   (bronze 3 %, silver 5 %, gold 7 %); уровень пересчитывается по сумме покупок
   (silver от 15 000 ₽, gold от 50 000 ₽).
6. **Отзывы** — клиент оценивает только завершённый визит, один отзыв на визит, не позже
   30 дней после визита.
7. **Аналитика** — выручка по филиалам и месяцам, рейтинг мастеров, загрузка смен,
   RFM-сегментация клиентов, когортное удержание, клиенты в зоне оттока,
   «злостные» неявки, популярность услуг.
8. **Пакетная загрузка клиентской базы** — импорт CSV из старых систем с валидацией
   каждой строки, журналом ошибок и отчётом о загрузке.

## 1.3. Ключевые бизнес-правила (инварианты)

| № | Правило | Где обеспечивается |
|---|---|---|
| BR-1 | У мастера не может быть двух пересекающихся по времени активных записей | `EXCLUDE USING gist` на `appointments` |
| BR-2 | У клиента не может быть двух пересекающихся по времени активных записей | `EXCLUDE USING gist` на `appointments` |
| BR-3 | Запись должна целиком лежать внутри смены мастера на эту дату | триггер `trg_appointments_validate` |
| BR-4 | Смена лежит внутри часов работы филиала; смену нельзя сократить/удалить, если «выпадают» активные записи | триггер `trg_work_shifts_validate` |
| BR-5 | Допустимы только разрешённые переходы статусов; финальные статусы неизменны; `completed`/`no_show` — только после начала визита | триггер `trg_appointments_validate` |
| BR-6 | Отмена — только с причиной | `CHECK` на `appointments` |
| BR-7 | Сумма оплат по визиту не превышает стоимость визита; оплата только завершённого/идущего визита | триггер `trg_payments_validate` |
| BR-8 | Бонусный баланс не может стать отрицательным; списание ≤ 30 % чека | `CHECK` + функция `complete_appointment` |
| BR-9 | Отзыв — только на завершённый визит, оценка 1–5, не позже 30 дней | `CHECK` + триггер `trg_reviews_validate` |
| BR-10 | Мастер может оказывать только активные услуги из своего прайса | функция `book_appointment` |
| BR-11 | Онлайн-запись не раньше чем за `min_lead_minutes` и не дальше `max_days_ahead` | функция `book_appointment` |

## 1.4. Функциональные требования к приложению

* CRUD для филиалов, категорий, услуг, мастеров (с настройками и прайсом), смен,
  клиентов, записей; проверка входных данных; фильтрация, сортировка, пагинация.
* Бизнес-сценарии: онлайн-запись по свободным слотам; завершение визита с оплатой и
  бонусами; отмена/неявка с историей статусов; отзыв о визите; пакетный импорт клиентов.
* Отчёты: 10 аналитических запросов + материализованное представление KPI с обновлением.
* Корректная обработка ошибок СУБД (коды SQLSTATE → HTTP-статусы).
* Документация API в формате OpenAPI 3.

## 1.5. Нефункциональные требования

* PostgreSQL 16, развёртывание через Docker Compose.
* Приложение подключается к БД под ролью `crm_app` с минимальными привилегиями;
  миграции выполняются ролью-владельцем `crm_owner`; секреты — только через переменные
  окружения (`.env`, не хранится в репозитории).
* Корректность при конкурентном доступе (двойное бронирование, потерянное обновление
  бонусного баланса).
* Время ответа операционных запросов (расписание дня, история клиента) — единицы
  миллисекунд на наборе ≥ 100 000 записей.
