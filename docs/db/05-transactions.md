# 5. Транзакции и конкурентный доступ

## 5.1. Составные бизнес-операции

| Операция | Изменяемые таблицы | Атомарность |
|---|---|---|
| Запись клиента — `crm.book_appointment` | `clients`, `loyalty_accounts` (триггер), `appointments`, `appointment_services`, `appointment_status_history` (триггер), `audit_log` | Одна функция в транзакции `db.InTx` |
| Завершение визита — `crm.complete_appointment` | `appointments`, `appointment_status_history`, `payments`, `bonus_transactions`, `loyalty_accounts`, `audit_log` | То же |
| Пакетный импорт — `staging.process_client_import` | `import_batches`, `import_errors`, `clients`, `loyalty_accounts` | Создание пакета, COPY и обработка — одна транзакция |

Транзакции приложения выполняет `internal/db.InTx`: `BEGIN` с нужным уровнем
изоляции → `SET LOCAL crm.app_user` → работа → `COMMIT`; при любой ошибке —
`ROLLBACK`, при `40001`/`40P01` — повтор до 3 раз.

## 5.2. Исследованные аномалии и механизмы защиты

### Аномалия 1. Двойное бронирование (нарушение бизнес-инварианта)

В исходном проекте (`services/booking/internal/repo/repo.go`) проверка выполнялась так:
`SELECT … FROM bookings WHERE barber_id = ? AND date = ? FOR UPDATE` → проверка
пересечений в Go → `INSERT`. На уровне READ COMMITTED это не защищает: если у мастера
на это время ещё нет записей, блокировать нечего, обе транзакции видят «свободно» и
обе вставляют пересекающиеся записи (фантом). Уникальный индекс
`(barber_id, time_start)` ловит только совпадающее начало, а не пересечение.

**Решение:** ограничение `EXCLUDE USING gist (barber_id WITH =, tstzrange(starts_at,
ends_at) WITH &&) WHERE (status NOT IN ('cancelled','no_show'))` (и такое же по
клиенту). Проверка ограничения учитывает незафиксированные строки других транзакций:
вторая транзакция ждёт исхода первой и после её COMMIT получает `23P01`. Решение
корректно при любом порядке операций и не требует повышения уровня изоляции или
глобальных блокировок. Отменённые записи и неявки в ограничение не входят — их время
снова доступно.

**Альтернатива:** уровень SERIALIZABLE (SSI). Наивная логика на SERIALIZABLE
корректна: PostgreSQL обнаруживает зависимость чтение-запись и прерывает одну из
транзакций с `40001`; `db.InTx` повторяет её, и повтор видит занятое время. Выбрано
ограничение EXCLUDE: оно декларативно, работает для любого клиента БД (не только для
кода, который не забыл выставить уровень изоляции) и не требует повторов.

### Аномалия 2. Потерянное обновление бонусного баланса

Чтение баланса в приложении → вычисление → запись: две параллельные оплаты бонусами
читают одно значение 500, обе списывают 400, итоговый баланс 100 — одно списание
потеряно.

**Решение:** в `complete_appointment` бонусный счёт блокируется
`SELECT … FOR UPDATE`, проверка достаточности выполняется после получения блокировки,
а сам баланс меняется атомарным `UPDATE … SET bonus_balance = bonus_balance + amount`
(триггер) под защитой `CHECK (bonus_balance >= 0)`. Вторая транзакция ждёт первую и
получает `CR009` (недостаточно бонусов). Аналогично триггер оплат блокирует строку
записи, чтобы две параллельные оплаты не превысили стоимость визита.

### Связанные гонки, закрытые блокировками

* Удаление/сокращение смены одновременно с записью на неё: триггер записи берёт
  строку смены `FOR SHARE`, триггер смены проверяет записи — операции упорядочиваются.
* Повторная отмена/завершение одной записи: функции берут строку записи `FOR UPDATE`
  и проверяют статус после блокировки.

## 5.3. Демонстрация

Команда `make core-demo-concurrency` (`go run ./cmd/concurrency-demo`) создаёт
одноразовую БД с контрольными данными и выполняет сценарии **двумя независимыми
подключениями A и B**, печатая хронологию. Фактический вывод:

```text

══ 1. Атомарность complete_appointment: откат при ошибке и успешное выполнение ══
       6 мс  [—] до операции:      статус=scheduled, оплат=0, бонус.операций=0, баланс=500.00, история=1
      13 мс  [A] списать 900 бонусов → ошибка: SQLSTATE CR009 → HTTP 422 insufficient_bonus: Недостаточно бонусов: запрошено 900, доступно 500.00
      14 мс  [—] после ошибки:     статус=scheduled, оплат=0, бонус.операций=0, баланс=500.00, история=1  (ничего не изменилось)
      22 мс  [A] списать 300 бонусов → успех: чек 2500, начислено 66, баланс 266
      23 мс  [—] после успеха:     статус=completed, оплат=2, бонус.операций=2, баланс=266.00, история=2

══ 2. Аномалия «двойное бронирование»: SELECT-проверка + INSERT без ограничения (READ COMMITTED) ══
       2 мс  [A] BEGIN; проверка пересечений для 10:00 → занято=false
      58 мс  [B] BEGIN; проверка пересечений для 10:30 → занято=false
     308 мс  [A] INSERT; COMMIT — запись создана
     361 мс  [B] INSERT; COMMIT — запись создана
     362 мс  [—] ИТОГ: у мастера 2 пересекающиеся записи (10:00–11:00 и 10:30–11:30) — инвариант нарушен
     362 мс  [—] причина: проверяемых строк ещё нет, FOR UPDATE блокировать нечего (фантом); обе транзакции видят «свободно»

══ 3. Решение: ограничение EXCLUDE (barber_id =, tstzrange &&) — конфликт и его обработка ══

       9 мс  [B] пытается записаться на пересекающееся время — ждёт исхода транзакции A…
      13 мс  [B] BEGIN; book_appointment(мастер 3, 2026-11-05 12:30, 45 мин)
     414 мс  [A] COMMIT
     415 мс  [B] ошибка: SQLSTATE 23P01 → HTTP 409 time_slot_conflict: conflicting key value violates exclusion constraint "appointments_barber_no_overlap"
     415 мс  [B] ROLLBACK; клиенту — «время уже занято», предложить другие слоты
     415 мс  [—] ИТОГ: одна запись; проверка ограничения учитывает незафиксированные строки других транзакций

══ 4. Альтернатива: наивная логика на SERIALIZABLE — ошибка сериализации 40001 и повтор ══
       4 мс  [A] попытка 1: BEGIN ISOLATION LEVEL SERIALIZABLE; проверка → занято=false

     206 мс  [A] INSERT выполнен, COMMIT…
     208 мс  [A] итог: запись создана
     237 мс  [B] INSERT → SQLSTATE 40001 → HTTP 503 concurrent_update: could not serialize access due to read/write dependencies among transactions
     260 мс  [B] попытка 2: BEGIN ISOLATION LEVEL SERIALIZABLE; проверка → занято=true
     261 мс  [B] итог: time_slot_conflict: время занято
     262 мс  [—] ИТОГ: записей 1. SSI обнаружил зависимость чтение-запись; db.InTx повторил транзакцию, повтор увидел конфликт

══ 5. Аномалия «потерянное обновление»: чтение баланса → вычисление в приложении → запись ══
       8 мс  [A] прочитан баланс 500, списываем 400
      40 мс  [B] прочитан баланс 500, списываем 400
     214 мс  [A] записан баланс 100, COMMIT
     243 мс  [B] записан баланс 100, COMMIT
     244 мс  [—] ИТОГ: списано 800 из 500, а баланс = 100 — обновление A потеряно

══ 6. Решение: SELECT … FOR UPDATE бонусного счёта в complete_appointment ══
      12 мс  [—] клиент 5: баланс 500; два незакрытых визита по 2000 ₽
      12 мс  [A] BEGIN; complete_appointment(визит 15, списать 400)
      20 мс  [A] выполнено, баланс в транзакции 148 (строка счёта заблокирована)
      20 мс  [B] ожидает блокировку бонусного счёта…
      20 мс  [B] BEGIN; complete_appointment(визит 16, списать 400)
     424 мс  [A] COMMIT
     424 мс  [B] ошибка: SQLSTATE CR009 → HTTP 422 insufficient_bonus: Недостаточно бонусов: запрошено 400, доступно 148.00
     424 мс  [B] ROLLBACK — визит не закрыт, клиенту предложено оплатить без бонусов
     425 мс  [—] ИТОГ: баланс 148 = сумма журнала 148; повторного списания нет
```

Что показано: (1) успешное выполнение и **полный откат** составной операции;
(2) воспроизведение аномалии двойного бронирования; (3) поведение при конфликте:
ожидание, `23P01`, откат, ответ `409`; (4) SERIALIZABLE: `40001` и повтор;
(5) аномалия потерянного обновления; (6) её предотвращение блокировкой.

Те же сценарии проверяются автотестами (`internal/store/concurrency_test.go`):
10 параллельных записей на пересекающееся время — ровно одна успешна, 9 получают 409;
два параллельных списания бонусов — ровно одно успешно, баланс равен сумме журнала.

## 5.4. Ручная демонстрация в двух терминалах psql

```sql
-- Терминал A                                   -- Терминал B
BEGIN;
SELECT crm.book_appointment('+79160000101', 'Клиент А', 1,
       (current_date + 1) + time '12:00', '{1}', 'phone');
                                                BEGIN;
                                                SELECT crm.book_appointment('+79160000102', 'Клиент Б', 1,
                                                       (current_date + 1) + time '12:30', '{1}', 'phone');
                                                -- ждёт…
COMMIT;
                                                -- ERROR: conflicting key value violates exclusion
                                                -- constraint "appointments_barber_no_overlap" (23P01)
                                                ROLLBACK;
```
